1. Résumé Exécutif

L'audit de sécurité interne d'AEGIS P2P v3.3.1 a été réalisé le 9 novembre 2026 par l'équipe Ares Maxima.

Cet audit s'inscrit dans notre engagement permanent de transparence et de rigueur technique. Il vient en complément des mécanismes de sécurité déjà intégrés au produit (vérification formelle AWS Kani, audits mémoire Miri, intégration continue 10/10).

Résultat : aucune vulnérabilité exploitable n'a été détectée dans le code d'AEGIS ni dans ses dépendances directes. Onze alertes automatiques ont été documentées et analysées : toutes sont soit des dépendances transitives du moteur Tor (maintenues par le Tor Project), soit des bibliothèques figées mais fonctionnelles (conformes aux standards NIST).

2. Périmètre de l'Audit

L'audit a couvert :

  • Le cœur cryptographique Rust (aegis-core) — 503 crates dépendants.
  • Les primitives post-quantiques : ML-KEM-1024 (FIPS 203), ML-DSA (FIPS 204).
  • Le moteur réseau Tor (Arti v0.18) et ses dépendances transitives.
  • L'APK Android compilé en mode release (signé, strip = true, panic = "abort").

Ce qui n'a pas été audité (prévu v3.4.0) : analyse dynamique avec Frida (hooks runtime), fuzzing exhaustif via cargo-fuzz, revue cryptographique par un tiers indépendant.

4. Analyse des Alertes Documentées

4.1 Vulnérabilités corrigées (4)

Grâce à l'exécution de cargo update, quatre vulnérabilités ont été corrigées par mise à jour de dépendances :

  • rustls 0.23.43 → 0.23.46 — 4 CVE corrigées (TLS 1.3 handshake, debug secrets, Brotli DoS, downgrade attack).
  • rustls-webpki 0.103.15 → 0.103.16 — Validation des certificats intermédiaires.

4.2 Vulnérabilités acceptées (3) — Dépendances Tor

Ces trois vulnérabilités proviennent exclusivement du moteur Tor (Arti v0.18). Elles ne peuvent pas être corrigées sans mettre à jour Arti lui-même (suivi en amont avec le Tor Project).

AdvisoryCrateSévéritéJustification
RUSTSEC-2026-0387crypto-bigint 0.5.5ThéoriqueAttaque par canal auxiliaire temporel nécessitant un accès physique ou une co-localisation. AEGIS n'appelle jamais directement crypto-bigint — usage uniquement via Tor.
RUSTSEC-2025-0009ring 0.16.20DoS mineurLe panic se produit uniquement avec overflow-checks activé. AEGIS compile en release avec overflow-checks = false (voir Cargo.toml, profil release).
RUSTSEC-2023-0071rsa 0.9.105.9 (medium)Attaque "Marvin" sur RSA PKCS#1 v1.5. AEGIS n'utilise pas RSA dans son propre code : tout est ML-KEM-1024 + X25519 + Ed25519. Tor utilise RSA uniquement pour la compatibilité avec certains relays legacy.

4.3 Warnings « unmaintained » acceptés (7)

Ces alertes signalent des bibliothèques qui ne sont plus maintenues par leurs auteurs, mais dont le code est stable et standardisé. Elles ne constituent pas des vulnérabilités actives.

  • Tor (5) : bincode, paste, ring 0.16, pqcrypto-internals, pqcrypto-traits — dépendances transitives du moteur Tor.
  • AEGIS (2) : pqcrypto-mlkem, pqcrypto-mldsa — implémentations ML-KEM-1024 et ML-DSA, conformes aux standards NIST FIPS 203/204. Le code upstream (PQClean) a été archivé mais reste fonctionnel et figeable.

Migration planifiée (v3.4.0) : remplacement de pqcrypto par les crates officielles ml-kem et ml-dsa (RustCrypto), qui sont activement maintenues.

5. Mesures de Sécurité en Place (au-delà de l'audit)

AEGIS P2P bénéficie de multiples couches de sécurité qui dépassent le seul audit de dépendances :

  • Vérification formelle AWS Kani — preuves mathématiques sur les primitives cryptographiques critiques (ML-KEM, Ed25519).
  • Audits mémoire Miri — détection exhaustive des comportements indéfinis (UB), sur 5 sous-systèmes.
  • Intégration continue GitHub Actions — 10 jobs automatisés à chaque commit (Miri, Kani, JNI symbols, Android NDK, TPM, Linux mmap, Valgrind).
  • Architecture « Zero-Disk » — aucune clé cryptographique ou donnée en clair ne touche le stockage persistant.
  • Attestation matérielle StrongBox — validation de la racine de confiance Android à chaque démarrage.
  • RAM polymorphique — masque XOR dynamique + structure « dual rail » avec canaris d'intégrité sur les buffers sensibles.
  • Builds reproductibles — tout client peut recompiler l'APK à partir du code source et vérifier le hash SHA-256.

6. Limites de cet Audit

En toute transparence, voici ce que cet audit interne ne couvre pas :

  • Pas d'analyse dynamique (hooks runtime, Frida, instrumentation live).
  • Pas de fuzzing exhaustif (prévu v3.4.0 avec cargo-fuzz).
  • Pas de revue cryptographique par un tiers indépendant.
  • Pas d'audit de l'interface Kotlin/Flutter (audit Rust uniquement).
  • Pas de test de pénétration réseau actif.

Un audit externe par un tiers indépendant reste recommandé pour les clients à exigences gouvernementales ou militaires. Ares Maxima prépare activement une candidature aux programmes d'audit gratuits (OTF Security Lab, Sovereign Tech Fund) pour financer cette étape.

7. Conclusion

AEGIS P2P v3.3.1 ne présente aucune vulnérabilité exploitable connue. Les onze alertes automatiques détectées sont documentées, justifiées, et leur exploitation est soit impossible dans l'architecture d'AEGIS, soit dépendante de conditions physiques (accès direct au device) hors périmètre du modèle de menace.

Ce rapport est publié en toute transparence, dans le cadre de notre engagement envers nos clients et partenaires. Il sera mis à jour à chaque version majeure.
